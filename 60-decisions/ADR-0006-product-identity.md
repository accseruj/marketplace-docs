# ADR-0006: Product identity model - canonical product with supplier offers

- Status: accepted
- Date: 2026-08-03
- Deciders: human
- Related: ADR-0005, 10-architecture/domain-model.md, INV-09, 00-product/vision.md

## Context
Each vertical storefront is fed by several suppliers. If two suppliers can deliver the same item, the system must decide whether the shopper sees one product or two listings. This single choice determines the shape of matching, pricing, stock computation, sourcing, order splitting and returns.

Launch reality, established in the Phase -1 elicitation round:
- 1-2 suppliers on the first vertical.
- Mixed channels: part REST/JSON API, part CSV/XML over SFTP.
- Supplier overlap at launch is therefore near zero.
- First vertical not yet chosen; identifier quality (GTIN/EAN/MPN) unknown until it is.

The decision cannot wait for that vertical research. It fixes the identity of every published product, and identity is the one thing that cannot be changed cheaply once a catalog is indexed.

## Options considered
| Option | Pros | Cons |
|---|---|---|
| A: 1 supplier item = 1 product | Simplest; no matching; no sourcing logic at order time | Duplicate listings compete with each other; cannibalised SEO; no failover when a supplier runs out; worse margin (cannot pick cheapest) |
| B: canonical product with many offers, best offer selected | One clean listing; supplier failover; margin optimisation; correct multi-supplier stock | Requires product matching (the hard part); sourcing decision logic; price can change when the winning offer changes |
| C: hybrid - canonical only where a reliable match key exists (GTIN/EAN/MPN), otherwise 1:1 | Pragmatic; matching only where it is trustworthy | Two code paths; inconsistent behaviour to reason about |

## Decision
Option B. One `CanonicalProduct` holds many `SupplierOffer`s.

Matching and offer selection are mandatory pipeline stages from day one, but degenerate while there is a single supplier:
- `canonical_key` at launch = `(supplier_id, supplier_item_id)`; each ingested item yields exactly one `CanonicalProduct`.
- Offer selection runs with exactly one candidate.

Option A was rejected as a starting point. It is not a cheaper architecture, it is a different identity. Migrating A to B later means merging published products on a live catalog - choosing a surviving SKU, 301-ing the loser, discarding its accumulated organic signals - across 10-20 storefronts, performed by one operator. Organic search is a primary acquisition channel (`00-product/vision.md`), so that cost is charged directly against revenue.

The incremental cost of B at launch is a canonical entity, an offer link and a projection step. The expensive part of B - matching logic - is not written until overlap exists. Option C is not a separate architecture either; it is this model with matching enabled only where a trustworthy key is present, and it remains reachable as an operating mode.

## Consequences

### Identity
- ID-01 Magento `sku` = canonical product id, format `CP-<ULID>`. Opaque, generated by the catalog data layer, never regenerated for the life of the product.
- ID-02 Magento `url_key` derives from `CanonicalProduct` content. Never from a supplier field.
- ID-03 Supplier item id lives only on `SupplierOffer`. It is what a purchase order carries; it never reaches a storefront URL or a Magento SKU.
- ID-04 Two `CanonicalProduct`s are never merged automatically. A merge is an explicit, audited operation that emits a 301. This is the only remaining place where identity change costs organic signal, and it is confined to correcting matching errors.

### Data ownership
- `CanonicalProduct` owns shopper-facing content. Supplier content is an enrichment input, not the record of truth. Otherwise a change of winning offer silently rewrites a live product page.
- Sellable stock is computed from offers via `SM-offer` state. Never copied from a feed field (INV-09).
- Retail price is computed from the selected offer's cost through `PriceRule`. Never copied from a feed field.

### Process
- `SourcingDecision` is persisted per order line even when there is one candidate offer. Required by automation-readiness test #2, independent of supplier count.
- Attaching a second supplier's offer to an existing `CanonicalProduct` is an ordinary ingestion event, not a migration.
- Moving to multi-sourcing is enabling the matching stage and the winning-offer rule. It is a configuration change, not a catalog rewrite.

### Costs accepted
- A catalog data layer owning canonical products and offers must exist before the first storefront goes live. It cannot be deferred. This constrains ADR-0005.
- Every published product carries an opaque SKU. Operator-facing search in the Magento admin must work on name, brand and supplier item id, not on SKU.
- `CP-<ULID>` requires ULID generation in the catalog data layer and a uniqueness guarantee across concurrent ingestion runs.

## Open within this decision
- OPEN: winning-offer rule - cheapest cost, shortest lead time, supplier priority, or composite score. Decidable only once a canonical product can carry more than one offer. Tracked in `10-architecture/domain-model.md`.
- OPEN: matching key strategy once matching turns on. Depends on identifier quality in the chosen vertical.
- OPEN: whether sellable stock sums across offers or exposes only the winning offer's stock. Coupled to the reservation strategy.

## Revisit triggers
- A second supplier's assortment overlaps the first: review the matching key, not this decision.
- Identifier quality in the chosen vertical proves too poor for any automatic matching: option C's split becomes the operating mode, still inside this model.
- Supplier overlap turns out materially different from the near-zero assumption used at launch.
