# Frontend (storefront platform)

## Shape
- Single multi-tenant Next.js App Router application (ADR-0002).
- Tenant resolved by `Host` header in `proxy.ts` (the Next.js 16 successor to `middleware.ts`), rewritten to an internal `[tenantId]` segment.
- Turborepo + pnpm workspaces.

```
apps/storefront/
packages/ui/               shared components, shadcn-style ownership
packages/magento-client/   GraphQL client + codegen types
packages/config/           per-tenant tokens, layout maps, route overrides, flags
packages/seo/              sitemap, robots, hreflang, JSON-LD helpers
```

## Differentiation model
- Same components everywhere. Differences expressed as:
  1. theme tokens (Tailwind + CSS variables)
  2. layout maps (which blocks, what order, per route archetype)
  3. route overrides (only when a layout map cannot express the flow)
- Forking a component per tenant is a design failure. Escalate to an archetype instead.

## Rendering strategy
- PLP: ISR / cached with short revalidate; filters as dynamic Suspense holes via Partial Prerendering.
- PDP: PPR - static shell (description, media) + dynamic holes (price, stock).
- Search: fully dynamic SSR, not cached.
- No full SSG across 20 catalogs; build time becomes unmanageable.

## SEO rules
- Self-referencing canonical per domain. Do not cross-domain canonicalise between tenants even when catalogs overlap - it collapses rankings onto one site.
- hreflang only for language/region variants of the same tenant; reciprocal, BCP 47 codes, no auto-redirects.
- Per-domain sitemap and robots, generated by `sitemap.ts` / `robots.ts`.
- JSON-LD rendered server-side, in the initial HTML. Product, BreadcrumbList, Organization first.

## Budgets
- LCP < 2.5s, INP < 200ms, CLS < 0.1 in field data, per route archetype.
- Third-party scripts are the main historical cause of CWV failure - each one needs justification.

## Risk to manage
- Blast radius: one bug affects all tenants. Mitigation: canary deploys, per-tenant feature flags, visual regression before merge.
